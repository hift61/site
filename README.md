# WATERful 공동 실험 분석

## 1 Hz 간격 예측 업데이트

CSV 분석의 **가상 실험 생성 → 주파수 간격별 예측**에서 시작 30 Hz, 끝 40 Hz, 간격 1 Hz를 선택합니다. 기본 조건당 20개로 생성하면 파도 조건 세 개가 모두 30~40 Hz를 지원할 때 총 660개가 저장됩니다. 이전의 **실측 조건에서만 생성** 방식도 선택할 수 있습니다. 기존 DB와 환경변수를 그대로 사용하므로 이번 업데이트에 SQL 재실행은 필요하지 않습니다. 저장된 과거 JSON은 유지되며 새 방식으로 다시 생성한 결과부터 확장 형식을 사용합니다.

파도 듀티와 변조도가 동일한 조건끼리만 묶습니다. 실측한 각 주파수에서 A/B별 거리–부호 있는 접근 속도의 선형 회귀 `mu=a+b*d`를 적합하고, 인접한 실측 주파수 사이에서 `mu(f,d)=(1-t)*mu_lo(d)+t*mu_hi(d)`로 보간합니다. 예를 들어 32 Hz는 30 Hz와 35 Hz 사이에서 `t=0.4`입니다. 요청 범위가 실측 범위를 벗어나면 해당 조건은 제외하며 주파수 외삽은 하지 않습니다. 이 모델은 총 이동 경로 길이로 계산한 평균 속력 모델이 아닙니다.

표본 생성 시 각 기준 주파수에서 실측 회차 하나를 선택하고 A/B 12개를 함께 사용합니다. 종류별 시작 거리 순위로 대응시켜 거리를 보정하고, 순위별 잔차 평균을 빼서 기대값을 회귀식에 맞춘 뒤 주파수 가중치로 결합합니다. 합성 표본의 A1~A6/B1~B6은 거리 순위이며 실제 특정 조각의 동일성을 의미하지 않습니다. 원본 회차와 원본 개체 번호는 `donors`와 `source_objects`에 보존합니다. 각 기준 주파수의 반복 회차가 한 개뿐이면 예측은 가능하지만 회차 간 변동을 추정할 수 없으므로 `warnings`에 표시합니다. 생성 수는 독립 실험 수가 아니며, 표본 분산을 신뢰구간으로 해석하면 안 됩니다. 두 주파수의 표본을 가중 평균하는 방식은 중간 주파수의 실제 변동성을 검증한 것이 아닙니다.

JSON은 기존 `synthetic`에 더해 `model`의 거리 회귀 계수·기준 주파수, `condition_summaries`의 거리 순위별 접근 확률, `generation_method`의 보간 여부, `source_case_counts`를 포함합니다. 접근 확률은 생성 표본 중 부호 있는 접근 속도가 0보다 큰 비율이며, 통계적으로 검증된 성공률은 아닙니다. 기준 주파수 중 하나라도 해당 거리의 실측 범위를 벗어나면 `distance_within_anchor_support=false`로 표시하므로 그 지점의 해석에 주의하세요. 확률은 생성 수와 시드에 따라 달라질 수 있습니다.

에너지는 선택한 두 원본 회차 모두 유효한 값이 있을 때만 주파수에 따라 보간합니다. 하나라도 누락되면 `energy_Wh=null`을 유지하며 0으로 대체하지 않습니다. 에너지 비교에는 같은 구동 시간의 실험만 사용하세요. 이 시간 조건은 현재 데이터 형식에 기록되지 않아 자동 확인하지 않습니다. 새 모델을 검증하려면 합성 표본과 원본 회차를 섞어 분할하지 말고, 독립 실측 회차를 통째로 제외한 평가와 중간 주파수 실측을 사용해야 합니다. 이번 기능은 중간 주파수 검증 점수를 생성하거나 보장하지 않습니다.

업데이트 파일은 `model.py`, `app.py`, `public/index.html`, `README.md`입니다. 기존 저장소의 같은 경로에 덮어쓰고 커밋하면 연결된 Vercel 프로젝트에 반영됩니다.

GitHub 저장소 루트에 압축을 풀어 업로드하세요. Vercel에서 해당 저장소를 Import할 때 Flask를 자동 감지하도록 Framework Preset은 자동 설정을 사용하고, Build Command와 Output Directory는 별도로 지정하지 않습니다. Python 함수 진입 파일은 프로젝트 루트의 app.py입니다. `public/`의 HTML과 CSV는 정적 파일로 제공됩니다.
Supabase 프로젝트 SQL Editor에서 schema.sql을 실행하고 Vercel 프로젝트 환경변수에 SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY (서버 전용 service_role 키), TEAM_PASSWORD (팀 전용 긴 임의 암호)를 추가한 뒤 배포하세요. 키·암호를 GitHub에 올리지 마세요. 한 팀이 암호를 공유하는 방식이며 개인별 권한·감사 로그는 제공하지 않습니다.
한 실험에서 A 6개와 B 6개를 동시에 측정합니다. 웹에서 12개 입력 양식을 받아 같은 case_id로 A1~A6, B1~B6의 시작 거리(mm)와 부호 있는 접근 속도(mm/s)를 입력하세요. 양수는 접근입니다. 같은 회차의 진동 주파수(Hz), 파도 듀티(0~1), 변조도, 에너지 완전성(true/false) 및 총에너지(Wh)는 각 행에 동일하게 입력합니다. 에너지가 누락되면 false로 하고 Wh 칸은 비워 둡니다. 서버에는 회차당 에너지 한 값만 저장합니다. 별도로 실시한 A 실험과 B 실험은 합치지 마세요.

같은 구동 조건에서 두 회차 이상 반복하면 종류별 거리-속도 회귀를 적합합니다. 합성 한 회차를 만들 때 한 실측 회차를 뽑아서 A/B 각각의 시작 거리 순위별 평균 거리에 맞춰 속도를 보정하고, 원래 개체 번호와 같은 회차 에너지를 보존합니다. 출력에는 12개 개별 속도, 종류별·전체 평균, 원본 회차 ID와 시드가 포함됩니다. 모델 검증용 실측 회차는 생성 전에 따로 보관하세요. 에너지는 실험 시간이 동일한 조건끼리 비교하세요.

여러 사용자가 동일한 케이스 ID를 저장하면 두 번째 업로드 전체가 취소됩니다. 새로고침하면 다른 사용자의 기록을 확인할 수 있습니다. 이전 6개 단독 실험은 기존 목록에서 조회할 수 있고 새 모델의 학습 자료에서 제외됩니다.

## 영상 업로드 및 평가

1. 기존 Supabase 프로젝트의 SQL Editor에서 `media_setup.sql`을 한 번 실행합니다. 영상 목록 테이블과 비공개 Storage 버킷을 준비합니다. 이미 이전 버전의 SQL을 실행했다면 이번 파일을 다시 실행해 영상 저장소 설정을 추가하세요. 기존 CSV 분석용 `schema.sql`은 신규 프로젝트에서만 별도로 실행합니다.
2. 수정한 파일을 기존 Vercel 프로젝트에 연결된 저장소의 배포 브랜치에 커밋합니다. 기존 환경변수 세 개를 사용합니다. 이전 패키지의 `api/index.py`나 경로 재작성 설정이 남아 있다면 제거합니다.
3. **업로드** 탭에서 영상·사진을 여러 개 선택하고 각 항목에 같은 회차의 `measurements.csv`와 선택 사항인 `case.json`을 붙입니다. 사진의 측정 CSV는 선택 사항입니다. **일괄 업로드**를 누르면 순서대로 전송합니다. 성공한 항목은 실험 목록에 표시되며 실패한 항목은 재시도할 수 있습니다. R2 연결 시 새 영상은 최대 2 GB까지 R2에 저장됩니다. Supabase에 남아 있는 영상도 계속 열 수 있습니다. 재생에는 H.264 MP4를 권장합니다.
4. 영상은 평가할 시점에서 **이 프레임 지정**을 누릅니다. 사진은 곧바로 지정할 수 있습니다. **A 지정**과 **B 지정**을 누르면 해당 그룹의 미지정 번호부터 진행합니다. 이미 지정한 번호를 누르면 해당 위치를 다시 찍을 수 있습니다.
5. **수조 지정**에서 왼쪽 위부터 시계 방향으로 꼭짓점 네 개를 표시합니다. **왼쪽 끝 휨**, **오른쪽 끝 휨**에서 각각 시작점·중간점·끝점을 찍습니다. 앱은 세 점을 지나는 곡선을 그려 직선 기준과의 차이를 표시합니다. 휘어 보이는 부분이 없는 쪽은 생략할 수 있습니다.
6. **임시 저장** 또는 **평가 완료**를 누릅니다. 같은 항목을 다시 열면 기준 프레임의 시각과 표시 좌표가 복원됩니다. 이 화면에서 표시하는 값은 수동 평가용이며, 렌즈 보정이나 부유물 자동 추적을 적용하지 않습니다.

평가 화면에서 연결된 원본 측정 CSV를 내려받을 수 있습니다. `case.json`에서 구동 구간을 확인하고 해당 구간의 측정값이 유효한 경우에만 소비 에너지(Wh)를 표시합니다. 이 값은 MDD10A 전원선 전체의 에너지입니다.

## 팀 영상 저장소 연결

1. Cloudflare Dashboard의 **R2 Object Storage**에서 **Standard** 버킷을 만듭니다. 예시 이름은 `waterful-videos`입니다. 비공개 상태로 둡니다.
2. 버킷 **Settings → CORS Policy**에 ZIP의 `r2_cors.json` 내용을 붙여넣습니다. 기존 사이트 `https://waterful-two.vercel.app`에서 쓰는 설정입니다. 주소가 달라졌다면 `AllowedOrigins`에 팀원이 접속하는 정확한 사이트 주소를 넣으세요.
3. R2의 **Manage API Tokens**에서 이 버킷만 선택하고 **Object Read & Write** 권한으로 토큰을 만듭니다. Vercel의 **waterful → Settings → Environment Variables**에서 Production에 아래 값을 넣습니다.

| 환경변수 | 값 |
| --- | --- |
| `R2_ACCOUNT_ID` | Cloudflare Account ID |
| `R2_BUCKET` | 만든 버킷 이름 |
| `R2_ACCESS_KEY_ID` | R2 토큰을 만들 때 발급되는 Access Key ID |
| `R2_SECRET_ACCESS_KEY` | R2 토큰을 만들 때 발급되는 Secret Access Key |

4. Supabase에서 최신 `media_setup.sql`을 실행한 뒤 이 버전을 배포합니다. 로그인 후 업로드 화면에 **공유 영상 저장소 연결됨**이 표시되면 R2 설정이 감지된 상태입니다. 영상을 한 건 올려 목록에서 재생해 확인합니다.

영상 원본은 R2에 저장되고 실험 정보, 측정 CSV, 평가 결과는 Supabase에서 관리합니다. 기존 Supabase 영상도 이전과 같이 열 수 있습니다. 웹앱은 팀 암호를 확인한 후 만료 시간이 있는 영상 주소를 발급합니다.

## Google Drive에서 실험 가져오기

Google Drive를 원본 영상 저장소로 쓸 수 있습니다. Drive에 팀 폴더를 만들고 팀원 Google 계정에 보기 권한을 부여합니다. 상위 팀 폴더 아래에 실험별 폴더를 하나씩 만들고 각 실험 폴더에 GoPro 영상 1개, `measurements.csv`, 가능하면 `case.json`을 넣습니다.

1. Google Cloud에서 프로젝트를 만들고 **Google Drive API**를 사용 설정합니다.
2. **Google Auth Platform**에서 OAuth 동의 화면을 설정합니다. 소규모 팀이라면 **External · Testing**을 사용하고 실제 팀원 Google 계정을 테스트 사용자 목록에 추가합니다. Drive 읽기 범위는 `https://www.googleapis.com/auth/drive.readonly`입니다.
3. **웹 애플리케이션** OAuth 클라이언트를 만들고 **Authorized JavaScript origins**에 `https://waterful-two.vercel.app`을 추가합니다. Vercel `waterful`의 Production 환경변수 `GOOGLE_DRIVE_CLIENT_ID`에 클라이언트 ID를 넣습니다.
4. 기존 Supabase에서 최신 `media_setup.sql`을 실행하고 GitHub에 변경 파일을 올려 배포합니다. **Google Drive에서 가져오기**에 상위 팀 폴더나 실험 하나의 폴더 링크를 붙여넣습니다. 팀원이 목록에서 Drive 영상을 열면 본인 Google 계정의 공유 권한으로 읽습니다.

영상은 Drive에 남고 웹앱에서 다시 복사하거나 업로드할 필요가 없습니다. 영상을 처음 열 때 파일을 브라우저로 읽어 재생합니다. 실험 정보, 측정 CSV, 평가 결과는 Supabase에 저장합니다. Drive 원본 영상의 내용을 바꾸면 기존 표시가 맞지 않을 수 있으니 분석할 원본은 그대로 두세요.

## 자동 추적 후 생성기에 등록

신규 배포에서는 `schema.sql`을 먼저 실행하고 `media_setup.sql`을 실행합니다. 이번 추적 보정 업데이트는 기존 DB 구조를 사용합니다.

1. 영상 평가에서 같은 회차의 `case.json`을 확인합니다. 영상과 측정 CSV만 올렸다면 평가 화면에서 `case.json`을 나중에 연결할 수 있습니다.
2. 기준 프레임에서 A1~A6, B1~B6의 중심과 수조 네 꼭짓점, 수면에서 거리를 잴 기준점인 진동원 중심을 찍습니다. 수조 실측 크기와 분석 종료 시각을 확인하고 **자동 추적 · 결과 저장**을 누릅니다.
3. 영상은 브라우저에서 분석합니다. 초기 중심 주변의 영상 패턴을 따라가고, 수조 네 점을 이용해 평면을 mm 단위로 변환합니다. 수렴 속도는 `(시작 거리 − 종료 거리) / 경과 시간`이며, 양수는 진동원에 접근한 경우입니다. 휜 벽 표시는 경계 검토용입니다. 광각 왜곡이 큰 영상은 분석 전에 보정하고, 카메라가 고정되어 있으며 부유물을 서로 구분할 수 있는 구간을 사용합니다.
4. 12개 모두 추적되면 동일 회차의 구동 조건과 함께 생성기에 등록됩니다. 불완전한 전력 로그의 에너지는 미확정으로 표시됩니다. 표시되는 에너지는 영상에서 선택한 구간이 아니라 측정 로그의 전체 구동 구간 기준입니다. 평가 화면에서 등록값과 마지막 위치를 확인할 수 있습니다.
5. 기본 설정은 추적과 저장을 자동으로 진행합니다. 추적을 놓치면 중간 시각의 영상과 넓어진 검색 범위에서 조각을 다시 찾습니다. 종료 위치가 확인된 조각의 속도를 저장하고, 나머지는 미확정으로 표시합니다. 생성기는 12개의 종료 위치가 모두 확인된 회차를 사용합니다.
6. 수동 검토가 필요하면 시작 전에 **미확정 조각을 저장 전에 영상으로 검토**를 선택합니다. 번호를 누르면 마지막으로 확인된 위치를 볼 수 있습니다. 재생 버튼 또는 시간 슬라이더로 움직임을 확인합니다. 종료 위치를 식별했으면 **종료 장면 보기**에서 중심을 찍습니다. 나머지는 **확인된 결과 저장**으로 건너뛸 수 있습니다.
7. 같은 영상에서 다시 등록하면 기존 등록값이 갱신됩니다. 다른 영상 또는 직접 올린 CSV에 같은 케이스 ID가 이미 있으면 충돌로 표시합니다. **CSV 분석**에서 같은 구동 조건의 독립 실험이 2회 이상이면 가상 실험을 생성합니다.
